Step 1 / 9

Confirm access

Confirm that you can deploy Azure resources, configure the Copilot agent, and install it in Teams using accounts in the same Microsoft tenant.

  1. Open Azure Portal. Confirm the subscription and approved Azure region.
  2. Open Power Apps and Copilot Studio. Confirm the same Microsoft tenant and Power Platform environment.
  3. Open Teams using an account in that tenant. Confirm it has a Teams license and can use custom agents.
  4. Have both release ZIPs, Zenity API credentials, organization/integration IDs, endpoint values, and a real violation ID available.
Resolve missing access before deploying. Keep credentials in your approved secret store and out of email, chat, and shared notes.
Continue when

The subscription, target environment, Teams account, and installation files are available.

Step 2 / 9

How it connects

The lookup service retrieves a finding from your Zenity organization and returns redacted context to Copilot Studio. The agent uses that context to explain the finding and provide general remediation advice.

Teams→Copilot Studio→Azure lookup→Zenity API
  1. One service is configured for one Zenity organization and integration.
  2. Zenity client credentials stay in Azure secrets. A separate random service key protects the connector endpoint.
  3. The service key permits reads in that scope. Limit who receives it and who can use the agent.
  4. Azure provides a generated HTTPS hostname. A custom domain and Nginx are unnecessary for this path.

Use the deployment files on this page with the packaged API-key connector. Keep the service key separate from the Zenity credentials. Complete the installation checks before granting additional reviewers access.

Continue when

The service has a fixed Zenity scope, separate credentials, and read-only access.

Step 3 / 9

Prepare Azure resources

Create or select a resource group, container registry, Container Apps environment, and managed identity in your Azure subscription.

  1. In Azure Portal, create or select an approved resource group.
  2. Create or select an Azure Container Registry. Use the existing registry’s authorization model.
  3. Create a Container Apps environment supporting the Consumption workload profile. Record its resource ID.
  4. Create a user-assigned managed identity. Record its resource ID. An authorized administrator must grant it image-pull access to the registry. For standard registry RBAC this is AcrPull; registries using repository ABAC require the corresponding repository reader assignment.
  5. Confirm your deploying account can assign this identity to the app, deploy the app, and build images in the registry. Use a local Azure CLI session authenticated to this subscription.
az login
az account set --subscription YOUR_SUBSCRIPTION_ID
az account show --query "{subscription:name,tenant:tenantId}" --output table

Resource creation, image builds, registry storage, logging, and the running app can incur Azure charges. The recipe uses one warm replica to reduce cold-start delays.

Continue when

The environment and registry exist, and the managed identity has the required image-pull access.

Step 4 / 9

Build the service image

Build a Python container from the release source and publish it to your Azure Container Registry. Keep credentials outside the build directory.

Extract the application source ZIP locally. Work from the directory containing connector_server.py and engine.py. Download into that directory.

mkdir lookup-build
cp connector_server.py engine.py profiles.py evidence.py live_guidance.py zenity_auth.py zenity_reader.py lookup-build/
if [ -f lookup_result.py ]; then cp lookup_result.py lookup-build/; fi
cp -R profiles lookup-build/
cp Dockerfile.lookup lookup-build/
az acr build --registry YOUR_REGISTRY_NAME \
  --image zenity-remediation-lookup:0.1.0-beta.1 \
  --file Dockerfile.lookup lookup-build
Container definition
FROM python:3.12-slim
WORKDIR /app
COPY . /app/
USER 10001:10001
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
EXPOSE 8080
CMD ["python3", "connector_server.py", "--live-config", "/run/secrets/connection.json", "--bind", "0.0.0.0", "--port", "8080"]

Use a clean release extraction. Do not add private configuration or credentials to lookup-build/.

Continue when

The registry build succeeds and the image exists in the intended registry.

Step 5 / 9

Configure and deploy HTTPS

Configure your Zenity connection and deploy the lookup container. Azure Container Apps provides the HTTPS hostname and certificate.

Download and . Keep the parameter file outside Git and shared folders. Restrict it before entering secrets:

chmod 600 lookup.parameters.local.json
  1. Open the parameter file in a secure editor. Replace every YOUR_... value. Use the Azure location, environment resource ID, managed identity resource ID, registry login server, and image built in the previous step.
  2. Set connection.organization_id, integration_id, API base, OAuth token URL, audience, and issuer to the values assigned to this Zenity environment. Preserve the trailing slash on the API base and exact issuer value. The region label does not select endpoints.
  3. Set zenityCredentials to the client ID and secret in its two-line format. Generate serviceKey with a secret manager, using at least 32 random characters. It must be separate from the Zenity secret.
  4. Review the template. It exposes HTTPS ingress, keeps the service key check active, mounts credential/configuration secrets, and uses one replica with 0.5 vCPU and 1 GiB memory.
az deployment group validate --resource-group YOUR_RESOURCE_GROUP \
  --template-file lookup-service.azure.json \
  --parameters @lookup.parameters.local.json

az deployment group create --resource-group YOUR_RESOURCE_GROUP \
  --template-file lookup-service.azure.json \
  --parameters @lookup.parameters.local.json \
  --query properties.outputs.hostname.value --output tsv

Record the returned hostname. Azure terminates HTTPS and forwards to container port 8080. The Python listener remains inside the container network. Follow your secret-retention policy for the local parameter file.

curl --silent --show-error --include https://YOUR_APP_HOST/api/lookup \
  --header 'Content-Type: application/json' \
  --data '{"violation_id":"00000000000000000000000000000000"}'

Expect 401 without a service key. The root path has no health page. Inspect revision status and system logs if the container cannot start; keep secret values and finding contents out of logs.

Continue when

Deployment succeeds, the revision is running, HTTPS works, and the unauthenticated request returns 401.

Step 6 / 9

Import and test the connector

Import the Copilot solution, set the connector hostname, and verify that it retrieves the expected finding.

  1. In Power Apps, select the target environment. Choose Solutions → Import solution and select the Copilot solution ZIP from the release. Wait for a success message.
  2. Open the imported solution, then Objects → Zenity remediation lookup. The editor may open in Power Automate.
  3. Choose Edit → General. Set Host to the Azure hostname without https:// or a path. Keep HTTPS and Base URL /. Choose Update connector.
  4. On Test, create a connection using the service key. Keep Zenity client credentials in Azure.
  5. Run LookupViolation with a real violation ID from the configured integration. Check outcome=ok, mode=live, and the exact violation and expected rule IDs.
  6. Return to Power Apps and choose Done if it says “Currently editing a Custom Connector.”
HTTP 200 alone is insufficient. A safe lookup failure may also use HTTP 200. Check the outcome and returned identifiers.
Continue when

The connector returns the correct live finding from your Zenity scope.

Step 7 / 9

Test and publish the agent

Connect the lookup tool and verify the agent’s response before publishing.

  1. Open the imported agent in Copilot Studio in the same environment. The imported name is Zenity Violations Agent Customer Draft.
  2. Open Tools → Read a Zenity finding for remediation planning. Complete the connection configuration. The packaged action uses user credentials, so reviewers may need to create or verify their authorized service connection.
  3. Keep Microsoft authentication enabled. Limit access to authorized reviewers for this service’s scope.
  4. Start a fresh test conversation and enter the real violation ID. Complete any connection verification prompt. Check the finding, rule, observation time, and general advice.
  5. Try an unknown ID. The agent must avoid inventing a finding. Publish after the live lookup succeeds.
Explain violation YOUR_REAL_VIOLATION_ID and give general remediation guidance.

The agent provides advice. It cannot apply remediation, approve an exemption, or establish that a change succeeded.

Continue when

The fresh Studio conversation produces finding-grounded advice and unknown IDs fail safely.

Step 8 / 9

Add and test in Teams

Install the agent in Teams and repeat the finding lookup with an authorized account.

  1. Open Channels → Microsoft 365 and Microsoft Teams. If hidden, use the extra tabs menu. In the newer designer, use Build → Channels → Add channel.
  2. Choose Teams only if that is the desired destination. Add the channel, then choose See agent in Teams or View in Microsoft Teams.
  3. Confirm Teams is signed in to the correct account and tenant. Add the agent for your own test.
  4. Start a new conversation, complete connection verification if requested, and enter the real violation ID. Compare the returned identifiers with the connector result.
  5. After the personal test succeeds, follow the customer’s Teams app approval and reviewer distribution process.
Continue when

Teams returns the same finding and general advice, without performing changes.
